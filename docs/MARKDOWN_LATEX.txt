================================================================================
 GITHUB MARKDOWN + LATEX (KATEX) RENDERING RULES
 A Global Reference (not tied to any one project)
================================================================================

WHY THIS FILE EXISTS
--------------------
GitHub does NOT hand raw $`...`$ or $$...$$ content straight to KaTeX.
The Markdown parser runs first and applies its OWN syntax rules (emphasis,
bold, list markers, table pipes, headings, backtick code spans, backslash
escapes) to the text BEFORE the math renderer sees anything.  Any byte
pattern that Markdown can interpret near a math delimiter can:

    (a) eat part of the math content  -> KaTeX error like
        "Missing open brace for superscript", or
    (b) break the math block detection entirely -> GitHub emits the
        RAW TEXT (you literally see "$...$" or "$$...$$" in the page).

Symptom (b) is the one that looks the worst: whole formulas appear as
plain text on GitHub while the same file looks perfect in a local editor.

This document records every failure mode, the exact byte patterns that
trigger it, and the exact fix.  Follow the ABSOLUTE RULES section (10)
and run the VERIFICATION SCRIPTS section (11) before committing or
publishing any documentation that contains math.

--------------------------------------------------------------------------------
1.  INLINE MATH: THE ONLY SUPPORTED FORM
--------------------------------------------------------------------------------

ALWAYS use the GitHub dollar-backtick form.  There is exactly ONE
correct byte pattern:

        `$CONTENT`$        (backtick, dollar, content, backtick, dollar)

Examples that are correct:

        $`gamma`$
        $`Q_\theta(s,a)`$
        $`V^{\ast}(s)`$
        $`n = 1`$

NEVER use:
        $CONTENT$            bare dollar form (not rendered as math)
        \(CONTENT\)          LaTeX inline form (not rendered)
        ``$CONTENT`$         extra backtick anywhere (breaks the span)

The backtick wrapper is what shields underscores, asterisks and braces
from the Markdown layer.  Without the backticks, _x_ becomes italics,
* becomes emphasis, { } becomes invisible.

IMPORTANT: an inline `$`...`$` span must live on a SINGLE physical line.
If it wraps across a newline and the continuation line begins with a
Markdown block marker (-, +, *, |, #, >, or "1."), the parser treats that
line as a bullet/heading/table and the span never closes -- GitHub shows
the raw text.  Even when the continuation starts with an ordinary letter
it renders only by luck.  Keep every inline span on one line.

--------------------------------------------------------------------------------
2.  DISPLAY MATH: THE ONLY SUPPORTED FORM
--------------------------------------------------------------------------------

ALWAYS use the GitHub fenced form.  $$ must be on its OWN line, with
nothing before or after:

        $$
        \large
        <math content>
        $$

Conventions that are required or strongly recommended:

  - The line right after the opening $$ is the \large directive.
  - A blank line must precede the opening $$ and follow the closing $$.
  - No blank line INSIDE the block.
  - Every line inside the block must not begin with a Markdown-special
    character (see section 4).  This is the single most common bug.
  - \begin{aligned} is allowed for multi-line derivations (rows end
    with \\ and use &= alignment).  \begin{cases}, \begin{bmatrix},
    \begin{pmatrix} are fine.

--------------------------------------------------------------------------------
4.  HAZARD:  THE ASTERISK  *  (emphasis)
--------------------------------------------------------------------------------

GitHub's Markdown emphasis parser consumes * characters even INSIDE
math.  A realistic example of the failure:

        $`V^*(s) = \max_a ...`$

The * in V^* was eaten as an emphasis delimiter, so KaTeX received

        V^(s)

and reported  "Missing open brace for superscript"  (the ( after ^ was
interpreted as the start of a braced group).

FIX:  never use a raw * as a superscript or a multiplication sign in
math.  Use:

        ^{\ast}      instead of   ^*    or  ^{*}
        \cdot        instead of   *     (multiplication)
        \times       instead of   *     (multiplication, when preferred)

A scan for the regex  \^\*  on any markdown file must return ZERO
matches.

--------------------------------------------------------------------------------
5.  HAZARD:  MARKDOWN LINE-START MARKERS INSIDE $$ BLOCKS
--------------------------------------------------------------------------------

Inside a $$ display block, ANY line whose first non-space characters
look like a Markdown block construct can make GitHub's math-block
detection fail, and the entire block is dumped as raw text.

Forbidden line starts (0-3 leading spaces are STILL dangerous; CommonMark
allows up to 3 spaces of indent for list markers):

        +   (followed by space)     list marker
        -   (followed by space)     list marker
        *   (followed by space)     list marker
        |                            table pipe
        #                            heading
        >                            blockquote
        1.  2.  etc. (digit-dot-space)   ordered list

Concrete failure examples:

  - a continuation line starting with:
        + \bigl(\varepsilon_{start} - \varepsilon_{end}\bigr)\,
    -> whole formula shown as raw text.

  - a line starting with:
         - \frac{1}{|\mathcal{A}|} ...
    -> same.

  - a block starting its math with a pipe:
        |G_t| \;\le\; ...
    -> the pipe was the hazard.  Fixed with \lvert G_t \rvert.

  - surrogate, soft-value and log-derivative style blocks each had
    continuation lines starting with  +  or  - .

FIX:  reflow the math so that no line inside $$ begins with any of the
forbidden characters.  Two equivalent techniques:

  1) Join the line so the + / - / | is no longer at line start.
     In display math a newline is just whitespace, so joining lines
     does not change the rendered formula at all.  Example:

        before:   = \varepsilon_{end}
                  + \bigl(\varepsilon_{start} - \varepsilon_{end}\bigr)\,
                  \max\!\Bigl(0,\; 1 - \tfrac{t}{T_{decay}}\Bigr).

        after:    = \varepsilon_{end} + \bigl(...
                  \max\!\Bigl(0,\; 1 - \tfrac{t}{T_{decay}}\Bigr).

  2) For a line that must START with an absolute value, replace
     the pipe delimiters with \lvert ... \rvert :

        before:   |G_t| \;\le\; \sum ...
        after:    \lvert G_t \rvert \;\le\; \sum ...

     (\lvert and \rvert render identically to | | in KaTeX.)

NOTE: a 4-space indent on a continuation line inside $$ is SAFE (a
block containing a length-three alignment kept its indentation and
reached KaTeX - it only failed because of the * issue above).  Do not
"fix" 4-space indents; aligned-derivation blocks with indentation
render fine.  Just avoid introducing NEW lines that start with
+  -  *  |  #  >  or 1.

--------------------------------------------------------------------------------
6.  HAZARD:  MALFORMED DELIMITERS  (stray / doubled backticks)
--------------------------------------------------------------------------------

Every inline math span needs EXACTLY one backtick on each side of the
dollar.  There are two common bugs of this class:

  (a) Double backtick before the closing dollar:
        $`(1 - \lambda)\, \lambda^{k-1}``$
      The span is never properly closed, GitHub shows raw text.
      FIX:  $`(1 - \lambda)\, \lambda^{k-1}`$

  (b) Stray trailing `` `$ `` with no matching opener:
        ...uses $`n = 2`-3`$
      The span $`n = 2` is fine; the trailing `$ is an orphan.
      FIX:  ...uses $`n = 2`$-3
      (close the span after 2, keep the "-3" as plain text).

RULE:  count the occurrences of the two-character sequence  `$  in a
file.  For every real math span it appears exactly twice (open + close).
The count must be EVEN.  The only legitimately unpaired occurrence is a
literal code-form description of the fence itself, e.g.  `$$...$$`  when
a document explains the syntax (that one contains a `$ with no partner).

--------------------------------------------------------------------------------
7.  HAZARD:  EMPHASIS / BOLD CROSSING A MATH SPAN OR A LINE BOUNDARY
--------------------------------------------------------------------------------

(a) SINGLE-ASTERISK EMPHASIS must NEVER straddle an inline math span.

    BROKEN:

        ...and the *advantage estimates were computed under $`\pi_\theta`$*,
        so they become stale.

    The * opened BEFORE the math span and closed immediately AFTER the
    closing backtick-dollar.  GitHub cannot interleave emphasis
    delimiters with the backtick-delimited math span, so the text around
    it rendered raw.

    FIX: remove the emphasis, or move it so it does not cross the span:
        ...and the advantage estimates were computed under $`\pi_\theta`$, 
        so they become stale.

    Safe pattern: emphasize a WORD, then math, then emphasize another
    word:
        *full* return $`G_t`$ with a *one-step* target      <- OK

(b) BOLD **...** must not OPEN on a line that ends right after a
    math-close, when the bold closes on the NEXT line.

    BROKEN:

        Classic RL maximizes expected return $`\sum \mathbb{E}[r]`.  **Maximum
        entropy RL** (Ziebart ...)

    FIX: reflow so the bold lives entirely on one line, starting it on a
    fresh line after the math-close:
        Classic RL maximizes expected return $`\sum \mathbb{E}[r]`.
        **Maximum entropy RL** (Ziebart ...)

    A well-rendered document contains ZERO math-close-then-emphasis
    line breaks.  Follow that.

Scan rules: a file must contain ZERO occurrences of the patterns
        `$*        (math-close immediately followed by asterisk)
        *`$        (asterisk immediately before math-open)
   and ZERO lines ending in  `$  whose next line starts with  **  or  *.

--------------------------------------------------------------------------------
8.  HAZARD:  BACKSLASH ESCAPING  (thin spaces and row breaks)
--------------------------------------------------------------------------------

Markdown's escape processing eats ONE level of backslashes before KaTeX
sees the content -- **but ONLY in display `$$` blocks.**  The rule is
NOT universal; it depends on which of the two math forms you used.

  - DISPLAY `$$...$$` blocks:  the sanitizer strips one backslash level,
    so to get a KaTeX thin space \, you must write TWO backslashes:
        \\,          (in the file, inside $$)  ->  \,  (seen by KaTeX)
    A single  \,  inside $$ becomes a plain comma by the time KaTeX
    sees it.  This is the documented GitHub-flavored Markdown
    convention, and it applies to every escaped punctuation command
    (\,  \!  \;  \:  \|  \{  \}  ...): DOUBLE it inside $$.

  - INLINE `$`...`$` spans:  the content is a Markdown *code span*, so
    backslashes are LITERAL and are passed to MathJax unchanged.  Here a
    SINGLE  \,  is correct:
        \,           (in the file, inline)     ->  \,  (seen by KaTeX)
    Writing  \\,  inline is WRONG: MathJax receives a row-break \\ then a
    literal comma.  (Verified against GitHub's own /markdown API: the
    display form strips one level; the inline code-span form does not.)

    Rule of thumb: DOUBLE the backslash inside $$, SINGLE inside $`..`$.

  - Matrix/array row breaks: to get a KaTeX \\ row break you must write
    FOUR backslashes in the file:
        \\\\         (in the file)  ->  \\  (seen by KaTeX)
    With fewer, every bmatrix row collapses onto one line.

  - A "\\" followed by "n" (e.g. \n) must never appear literally inside
    a real math block; it is only used in prose when DESCRIBING the
    fence syntax, e.g.  `$$\n\large\n...\n$$`  inside backticks.

--------------------------------------------------------------------------------
9.  HAZARD:  NAMED OPERATORS AND UNICODE
--------------------------------------------------------------------------------

  - GitHub's renderer does NOT support \operatorname.  Use upright
    \mathrm{...} for multi-letter operator names:
        \mathrm{clip}, \mathrm{KL}, \arg\max, \max, \mathbb{E}

  - All math symbols must be LaTeX, never raw unicode, in math position:
        \pi  NOT  the pi character
        \theta  NOT  theta character
        \gamma  NOT  gamma character
        \to  NOT  an arrow character
        \le  NOT  <= or a unicode <=
    Prose may use normal unicode punctuation (em-dash, section sign,
    ellipsis, etc.).

--------------------------------------------------------------------------------
10.  ABSOLUTE RULES - CHECKLIST BEFORE COMMITTING DOCS WITH MATH
--------------------------------------------------------------------------------

[ ] every inline math span is exactly  `$...`$   (one backtick each side)
[ ] zero occurrences of the regex   \^\*        (no ^* or ^{* anywhere)
[ ] zero bare * used as multiplication inside math (use \cdot / \times)
[ ] inside every $$ block, no line starts (after 0-3 spaces) with
    +  -  *  |  #  >  or  digit.
[ ] absolute values at the start of a display line use \lvert \rvert
[ ] \large is the first content line of every display block
[ ] no blank line inside any $$ block
[ ] emphasis and bold never straddle a math span; bold never starts on a
    line right after a math-close
[ ] no inline `$`...`$` span crosses a newline, and no continuation line
    starts with + - * | # > or digit. (a cross-line span whose second line
    begins with "- " is parsed as a bullet list and renders raw)
[ ] thin spaces: DOUBLE backslash \\, inside $$ DISPLAY blocks; SINGLE
    backslash \, inside inline $`...`$ spans; row breaks \\\\ in arrays
[ ] named operators use \mathrm (never \operatorname)
[ ] no raw unicode math symbols
[ ] symbol table + formulas verified by running the verification
    scripts below on the file(s)

--------------------------------------------------------------------------------
11.  VERIFICATION SCRIPTS  (run before committing; Python 3)
--------------------------------------------------------------------------------

Run the linter script, which implements every check below (plus the rules
in sections 1-9) and reports ``file:line:col: [R<n>] message``:

    python scripts/check_md_math.py            # all *.md, report only
    python scripts/check_md_math.py --fix      # apply the safe fixes
    python scripts/check_md_math.py --json     # machine-readable

It exits 0 when clean, 1 when it finds anything, 2 on a usage error, and
it is wired into CI as a blocking step.  The historical ad-hoc snippet
that used to live here was superseded by the script; it is preserved in
git history if you need the reference.

The checks it performs, in the script's own numbering:

  R1   bare ``$...$`` / ``\\(...\\)`` / `` ``$ `` extra backtick
  R2   an inline ``$`...`$`` span crossing a newline
  R3   ``$$`` not alone on its line; missing ``\\large``; blank line
       inside the block; missing blank line before/after
  R4   ``^*`` or ``^{*}`` (must be ``^{\\ast}``)
  R5   a ``$$`` line starting with ``+ - * | # >`` or a digit
  R6   malformed delimiters: `` ``$ ``, stray trailing `` `$ ``, a
       stray backtick inside a span
  R7   a single ``*`` straddling a math span; a math-close at end of
       line followed by emphasis on the next line
  R8   display ``\\,`` that must be ``\\\\,``; inline ``\\\\,`` that must
       be ``\\,``
  R9   ``\\operatorname``; raw unicode math symbols and ASCII
       ``>= <= ->`` in math position
  R10  a ``$$`` line-start ``|...|`` absolute value

Fenced code blocks and inline code spans are literals: the linter never
checks them, which is also how a document may legitimately *show* a
broken example.

--------------------------------------------------------------------------------
12.  CLOSING NOTE
--------------------------------------------------------------------------------

If ANY item on the checklist in section 10 fails, or ANY check in the
scripts in section 11 reports a problem, fix the file BEFORE you commit
or publish it.

The symptoms to recognize:
  - a KaTeX error message ("Missing open brace ...", "Unknown
    operator ...") means Markdown already mangled the math content;
    inspect the bytes around the offending span.
  - raw "$...$" / "$$...$$" text visible in the rendered page means
    math-block detection failed; look for line-start markers,
    malformed backticks, or emphasis/bold crossing span boundaries.
  - a COMMA suddenly visible inside a rendered formula (for example
    "$\,$" showing up as a comma) means Markdown ate the backslash of
    an escaped punctuation command; see item 3.

With the checklist and the scripts, none of these problems should ever
reach a reviewer again.
